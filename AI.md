# AI usage

I built this project with **Claude Code** (an AI coding agent in my terminal/IDE) as a pair programmer.
I made the product and architecture decisions, reviewed every file, tested each feature by hand, and
kept the AI working in small steps so I understood and could defend every line.

## How I worked

- **Feature by feature, one commit each.** After every feature (config, signup, signin, guard, ...)
  the code was built, linted, tested with curl or in the browser, then committed and pushed.
  The git history shows that progression.
- **The AI proposes options, I decide.** For every choice with real alternatives I asked for the
  options and trade-offs first, then picked:
  - React + Vite (over Vue), Mongoose (over Prisma / TypeORM)
  - JWT in an **httpOnly cookie** (over localStorage) for XSS safety
  - **MUI** for the UI. The AI recommended Tailwind, I chose MUI for ready-made accessible components.
  - bcrypt (over argon2), auto-login after sign-up, react-hook-form + zod, a small fetch wrapper (over axios / TanStack Query)
- **Explain, then accept.** I had it explain each file line by line before moving on.

## Which parts were AI-assisted

Most of the code was generated by the AI and then reviewed, run and adjusted:
scaffolding (Nest CLI, Vite template), DTOs and validation rules, the auth service and JWT guard,
the exception filter and logger, Swagger setup, React pages and forms, tests, the CI workflow and the README.

My own work was the decisions above, reviewing and testing every step, and steering it away from
over-engineering (no refresh tokens, no Passport, no global guard, no extra state library).

## Prompts and approaches that worked well

- *"Do it feature by feature, no over-engineering, I need to understand every line, tell me when there are options."*
  This one sentence set the whole working style.
- *"Different features should be different commits on GitHub, not one commit at the end."*
  I gave this correction after the first feature, when the AI hadn't committed yet.
- Asking for **verification after every feature** (curl for the API, clicking through in the browser
  for the UI) caught problems immediately instead of at the end.
- When something failed, asking it to **reproduce the problem in isolation** before changing code
  (see the MongoDB driver issue below).

## What I had to correct or rework

Things the AI got wrong or that only showed up when running the code:

1. **Wrong types for env variables.** It wrote `config.getOrThrow<number>('JWT_EXPIRES_IN')`. Env vars are
   always strings, so the generic lied about the type. Changed to `Number(...)`.
2. **An unnecessary workaround.** It stripped `maxAge` before `res.clearCookie()`. Reading Express 5's
   source showed `clearCookie` already does that, so the workaround was removed.
3. **zod rule order.** `z.email().trim()` checks the format *before* trimming, so `" a@b.com"` failed.
   Fixed with `z.string().trim().pipe(z.email())`.
4. **Newest isn't always right.** The latest Vite template (Vite 8 + TypeScript 7) crashed `npm install`
   because of an npm 10 bug. I chose the stable Vite 6 template instead of forcing it, so reviewers and CI won't hit the same crash.
5. **Version mismatches with Nest 11.** `@nestjs/swagger` v12 needs Nest 12, so I pinned v11 instead of
   using `--legacy-peer-deps`. Later the tests showed that `@nestjs/jwt`, `@nestjs/config` and
   `@nestjs/mongoose` v12 are **ESM-only**: the app only ran thanks to Node's `require(esm)`, and Jest
   couldn't load them. All were pinned to their Nest 11 versions. The same applied to `@hookform/resolvers` (v5 instead of v6).
6. **MongoDB driver 7 vs Jest.** The e2e tests failed with *"Missing required sub-document 'driver'"*.
   Rather than guess, we narrowed it down: BSON works in Jest, the metadata is correct, the plain driver
   connects outside Jest but fails inside it. So it's driver 7 + Jest, not our code. Switched to
   Mongoose 8 (driver 6), which `@nestjs/mongoose` supports.
7. **A real behaviour found by a test.** The e2e test expected two password errors, but the API returned one:
   class-validator keys errors by constraint name, so several `@Matches` rules collapse into one message.
   I decided this is acceptable (the user sees the next rule after fixing the first), documented it in the DTO
   and made the test assert the real behaviour.
8. **MUI v9 API change.** The AI used `fontWeight` / `textAlign` props, which MUI v9 removed. Moved to `sx`.
9. **Lint caught type holes.** `req.cookies` is `any` (cookie-parser types), and `user.id` is untyped in
   Mongoose 8. Fixed with an explicit cast and `user._id.toString()`.

## Decisions I made differently from the AI

- **MUI instead of Tailwind** (the AI's recommendation).
- **No frontend unit tests.** The AI started adding Vitest. I stopped it and spent the time on manual
  end-to-end checks in the browser instead. The backend has unit and e2e tests that run in CI.
- **Commit per feature from the start**, which the AI wasn't doing until I asked.

## Takeaway

AI made the boilerplate and scaffolding very fast. The value I added was in the decisions, in
running and checking everything, and in not accepting a fix until we understood the root cause
(version pins instead of `--force`, reproducing the driver bug instead of guessing).
